# 版本升级

从经过审查的固定提交发布，每次升级先在独立测试环境完成类型检查、测试和构建，
再验证相关账号、命令和文件流程。

## 保持实例连续性

升级应用代码时沿用：

- 固定 `BRIDGE_ISSUER`、MCP 地址、OAuth subject 与账户别名。
- 签名 JWKS/kid、状态加密密钥、密码哈希、Cron secret 与应用 secret。
- 飞书 app/user 绑定及 scopes、Upstash 连接、namespace、Blob store。
- 最新持久状态：用户令牌、OAuth grant、上传清单和写入回执。

格式标识和密钥派生上下文属于持久协议，版本更新时保持稳定；涉及格式变化的版本，
按对应说明准备备份和恢复方案。协议回归使用合成数据验证。

## 发布与回退

1. 记录当前生产部署及待发布提交，按顺序发布。
2. 在独立测试环境验证改动，使用明确的生产配置构建和发布。
3. 用已有客户端验证连接，以及本次涉及的读取、文件、授权或维护流程。
4. 观察 HTTP 状态、stateOps、续期提示和服务商用量。遇到存储故障，检查连接配置、
   服务状态和配额，保留现场授权状态。
5. 需要回退时，恢复已验证的应用版本并继续使用最新持久状态，接续已经轮换的令牌。
   涉及持久格式变化时同时执行该版本的恢复步骤。

日常观察见 [运维与用量](operations.md)。

## 分钟级写入回执协议

新请求使用目录返回的 `writeRequest.requestId`，形如 `w2_<Unix 毫秒>_<唯一后缀>`。
这是写入协议变更：旧的任意字符串 ID 被明确拒绝，并返回新格式建议；先核对旧请求
是否已经执行，不能自动换 ID 重写。工具目录应刷新，既有 OAuth 登录无需改变。

新回执在同一 namespace 的 `state/v2/mutations/<摘要>.json` 下独立加密存储，Redis
自动到期；不再使用整份 `state/v1/mutations.json` 的 256 条/1 MiB 容量。旧 v1
回执暂留原地，旧格式请求不会进入新执行路径；每日维护删除已超过 60 分钟的旧记录。
该期限也给旧部署中的在途调用留出收尾时间，不需要清空回执才能恢复新写入。

新回执的存储 TTL 为请求有效期 60 分钟加 5 分钟收尾时间。请求有效期不会随重试延长；
过期请求在存储查询前即拒绝，因此不需要永久保留去重标记。运行中/不确定结果不会因
租约结束自动再次执行。分块上传暂存的 24 小时清理期限不等于提交期限。

回退时不能让旧协议直接接管写入：旧版不识别新回执，也不拒绝过期的新 ID。应先开启
维护模式，再前向修复或使用同样理解 v2 协议的版本；保留最新授权状态。不要恢复旧
Redis 快照、复制回执到旧格式或清空记录后重新提交未核对的动作。
